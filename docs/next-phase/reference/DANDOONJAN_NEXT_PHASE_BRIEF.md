# دستورکار فاز بعدی DANDOONJAN برای صادقی

## هدف

نسخه بعد باید دو خروجی قابل بررسی داشته باشد:

1. بازطراحی کامل تجربه کاربری بر اساس چهار تصویر مرجع این پوشه.
2. اجرای واقعی یک پرونده کامل ناشناس با API چندوجهی و تولید دو گزارش مجزا برای بیمار و دندان‌پزشک.

این فاز هنوز برای تشخیص قطعی، استفاده بالینی مستقل یا انتشار عمومی تأیید نشده است. خروجی تشخیصی باید به‌صورت احتمال‌های رتبه‌بندی‌شده، شواهد، عدم‌قطعیت و بررسی‌های تکمیلی ارائه شود.

## تصاویر مرجع

- `01-tooth-beauty-landing.png`: زیبایی دندان به‌عنوان قهرمان هویت بصری
- `02-digital-dossier-builder.png`: کامل‌کردن پرونده دیجیتال حول دندان مرکزی
- `03-digital-analysis.png`: خواندن مدارک و اتصال نتیجه به منابع
- `04-glass-results.png`: نتیجه شیشه‌ای و خروجی جداگانه بیمار/دندان‌پزشک

تصاویر art direction هستند، نه فایل آماده برای کپی پیکسلی. متن نهایی باید در HTML واقعی و با فونت فارسی خوانا پیاده شود؛ متن داخل تصاویر نباید به‌صورت bitmap وارد محصول شود.

## قرارداد بصری غیرقابل‌مذاکره

- شخصیت: لوکس، مینیمال، جسور، مدرن و سینمایی.
- مهم‌ترین اصل: زیبایی طبیعی دندان قهرمان احساسی و بصری کل محصول است. دندان باید مانند یک جواهر زنده، سالم، نورانی و دقیق دیده شود؛ نه نمونه آزمایشگاهی.
- پالت: مشکی زغالی، سفید خالص/مرواریدی و مسی؛ بدون گرادیان‌های آبی/بنفش و ظاهر cyberpunk.
- بدون انسان، چهره، دهان یا تصاویر stock.
- فقط خود دندان می‌تواند آناتومیک باشد؛ جمجمه، بدن، صورت و سیلوئت انسانی ممنوع است.
- دندان سه‌بعدی نیمه‌واقع‌گرایانه در مرکز تجربه؛ enamel طبیعی، مرواریدی و لوکس، و فقط هنگام تحلیل یک برش هولوگرافیک محدود.
- هیچ کاغذ کرمی، بژ، پرونده قدیمی، parchment یا حس آرشیوی مجاز نیست.
- مدارک کاملاً دیجیتال و به‌شکل لایه‌های شیشه‌ای دودی/شفاف با متن سفید خالص باشند و با خطوط پزشکی ظریف به دندان متصل شوند.
- فضای تیره فقط قاب دندان است؛ سنگ، غار، صحنه تاریک سنگین و تزئینات خشن ممنوع است.
- ساختار ادیتوریال و فضایی باشد؛ dashboard، sidebar، KPI، card grid و فرم wizard معمولی ممنوع است.
- تیتر فارسی ادیتوریال و شخصیت‌دار؛ متن بدنه هندسی، ساده و خوانا.
- motion جسور و سینمایی است، ولی `prefers-reduced-motion` و fallback بدون WebGL الزامی است.
- موبایل نباید نسخه فشرده دسکتاپ باشد؛ ترتیب روایت باید برای عرض 390 دوباره چیده شود.

## جریان محصول

### 1. شروع

- Hero با یک دندان مرکزی و CTA اصلی «ساخت پرونده».
- CTA دوم برای «مشاهده پرونده نمونه» باقی بماند.
- از همان ابتدا مشخص باشد که محصول شواهد را توضیح می‌دهد و جایگزین معاینه نیست.

### 2. ساخت پرونده کامل

کاربر بتواند حداقل موارد زیر را جداگانه اضافه کند:

- شرح علائم و مدت آن‌ها
- سابقه پزشکی، داروها و حساسیت‌ها
- طرح درمان یا نسخه در قالب متن، تصویر یا PDF
- رادیوگرافی و تصاویر دندان
- گزارش‌ها و درمان‌های قبلی
- سؤال اصلی کاربر

پرونده باید progressive باشد: ورودی کم مجاز است، ولی UI به‌وضوح نشان دهد چه اطلاعاتی برای تحلیل دقیق‌تر کم است. اطلاعات هویتی بیمار نباید برای تست استفاده شود.

### 3. تحلیل واقعی

- مسیر mock برای تست‌های deterministic حفظ شود، ولی یک مسیر واقعی end-to-end نیز الزامی است.
- provider باید multimodal و قادر به دریافت متن و تصویر باشد.
- تماس provider فقط از backend انجام شود؛ API key هرگز در frontend، repository، log، screenshot یا پاسخ API نمایش داده نشود.
- کلید تست صادقی فقط در secret/environment محلی یا محیط preview قرار گیرد و commit نشود.
- نسخه تحویلی باید با یک environment variable قابل اتصال به کلید مالک پروژه باشد.
- timeout، retry محدود، خطای قابل‌فهم و fail-closed حفظ شود؛ در خطای provider نباید نتیجه ساختگی به‌عنوان نتیجه واقعی نمایش داده شود.
- نام provider، model، زمان اجرا و شناسه run برای audit ذخیره شود، بدون ذخیره prompt یا محتوای حساس در log.
- قبل از ارسال، metadata و نام فایل‌ها sanitize شوند. داده واقعی فقط در صورت ناشناس‌سازی و مجوز استفاده وارد provider شود.

## قرارداد خروجی API

پاسخ ساختاریافته حداقل شامل این بخش‌ها باشد:

```json
{
  "patient_summary": {},
  "professional_report": {},
  "diagnostic_hypotheses": [
    {
      "label": "",
      "confidence_label": "LOW|MEDIUM|HIGH",
      "supporting_evidence_refs": [],
      "contradicting_evidence_refs": [],
      "missing_information": [],
      "recommended_checks": []
    }
  ],
  "safety_red_flags": [],
  "limitations": [],
  "source_index": []
}
```

- score عددی نمایشی ممنوع است مگر مدل و روش آن جداگانه اعتبارسنجی شده باشد.
- هر ادعا باید حداقل یک `source_ref` معتبر داشته باشد یا صریحاً «بدون پشتوانه کافی» علامت‌گذاری شود.
- مدل اجازه اعلام تشخیص قطعی یا تجویز مستقیم درمان ندارد.
- خروجی بیمار ساده و کوتاه باشد؛ خروجی تخصصی شامل شواهد، ناسازگاری‌ها، فرضیه‌ها و بررسی‌های لازم باشد.

## تست واقعی پذیرش

یک پرونده کامل و ناشناس با این اجزا آماده شود: شرح علائم، سابقه، طرح درمان، یک رادیوگرافی مجاز برای تست و یک گزارش قبلی. سپس این مسیر ضبط و مستند شود:

1. ایجاد پرونده و آپلود همه مدارک.
2. اثبات اینکه provider واقعی اجرا شده و run در حالت `mock` نیست.
3. تولید احتمال‌های رتبه‌بندی‌شده با ارجاع به منابع.
4. نمایش اطلاعات ناقص و بررسی‌های تکمیلی.
5. تولید «خلاصه برای شما» و «گزارش تخصصی» از یک snapshot مشترک.
6. restart برنامه و بازشدن دوباره همان نتیجه بدون تغییر شناسه‌ها و منابع.
7. اجرای خطای عمدی provider و اثبات fail-closed بودن UI.
8. بررسی logها برای نبود کلید، نام بیمار، متن پرونده، URL اتصال و محتوای تصویر.

این تست برای ارزیابی فنی است، نه تأیید صحت بالینی. برای سنجش صحت تشخیصی باید پاسخ مورد انتظار پرونده توسط دندان‌پزشک واجد صلاحیت ثبت و با خروجی مقایسه شود.

## معیار پذیرش UI

- چهار نمای اصلی از نظر composition، hierarchy، palette و motion به رفرنس‌ها نزدیک باشند.
- مسیر کامل در عرض‌های 390، 768 و 1440 بدون overflow کار کند.
- navigation با صفحه‌کلید، focus واضح، contrast مناسب و reduced-motion پاس شود.
- دندان سه‌بعدی نباید مانع تکمیل پرونده شود؛ fallback تصویری سبک الزامی است.
- متن نتیجه از حالت تکراری فعلی خارج شود و progressive disclosure داشته باشد.
- PDF شامل خلاصه بیمار، گزارش تخصصی، منابع، محدودیت‌ها و زمان/model run باشد.

## تحویل مورد انتظار

- Pull Request جداگانه روی آخرین RC، بدون merge یا production deploy خودکار.
- لینک preview فعال با API واقعی server-side برای تست مالک پروژه.
- یک اجرای ثبت‌شده از پرونده ناشناس و فایل PDF خروجی.
- نتایج تست‌ها و فهرست دقیق موارد `NOT VERIFIED`.
- دستور کوتاه تنظیم provider برای مالک پروژه، بدون اشتراک یا commit کلید.
